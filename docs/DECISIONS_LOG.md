## ADR-011 — Phase 3 multi-model orchestration: architect/worker, tiered window control, scoped memory, VS Code plan, OmniRouter
2026-11-26 · Status: Accepted
Context: The maintainer asked (2026-11-26) for OpenCobot to orchestrate work across many models from one place: a user-chosen "architect" model (e.g. a Pro Codex/Claude account) decomposes a task and delegates subtasks to worker models (local Ollama models, CLI providers, free tiers, aggregators), with results brought back into the VS Code workspace; the platform's own memory should track what the user is doing; window control must be FAST (accessibility tree / UI Automation, not screenshots); the control plane must stay lightweight enough for low-spec laptops (no GPU, no 32 GB RAM); and the user picks the architect in the UI. Phase 2 already provides the pieces this builds on: the policy-aware gateway with per-role routing, CLI-model providers, budgets + fallback chains + circuit breakers, the daemon on localhost, the 22 tools with execute()+verify(), SQLite memory, and policyd authorization. What is missing is the orchestration layer itself (decomposition, scoped dispatch, verification-before-integration), the fast window-control backends, and the VS Code surface.
Decision: (a) Orchestrator (`core/orchestrator.py`): a thin layer over the existing `Gateway` + `Runtime`, never a second model-calling path. The architect is a user-chosen provider name from gateway config (top-level `"orchestrator": {"architect": "<provider>", "workers": [...]}` in `gateway.json`, read by `load_orchestrator_config()`; default architect is the PLANNER role's provider, set via the existing `Gateway.set_role_provider`). Decomposition: the architect returns JSON `{"subtasks": [{"title", "goal", "context", "provider" (hint, may be null), "output": {"kind": "file"|"text", "path"?}, "checks"?}]}`; unparsable output is retried once, then the orchestrator falls back deterministically to one subtask (the whole task). Context scoping: each subtask carries only its own `goal`/`context` plus the top-level task title — never the full history or memory dump. Dispatch: per subtask, the orchestrator sets the EXECUTOR role provider to the hinted worker (public `set_role_provider` API) and calls the existing `Gateway.complete("EXECUTOR", ...)` — so CLI providers, budgets, the cloud pre-approval gate (R-021) and the fallback chain are all reused, not re-implemented. Budget exhaustion: `complete()` already skips exhausted providers and walks the chain; when the whole chain is exhausted the subtask is marked `queued` (with reason) and the run continues with the other subtasks; `retry_queued()` re-attempts them later. Verification before integration: every worker output is verified first — deterministic shape checks, plus declared `checks` (argv commands, run through `Runtime.run_tool`, i.e. policy-gated) and/or an architect review via the VERIFIER role; the verdict (method + evidence) is recorded on the subtask and in memory. Output that fails verification is NEVER integrated; it gets one re-dispatch with the verification evidence as feedback, then is reported as failed. Conflicts: when two workers produce overlapping output for the same file, the architect resolves (it sees both outputs and the verification evidence) and only the winning version is integrated. Integration: only via `Runtime.run_tool` (`write_file`/`create_file`, Level 2, policy-gated), only into the workspace directory (paths are resolved and must stay under the workspace root), and only when `verification.passed` is true — `integrate()` refuses otherwise (fail closed). No orchestrator tool use bypasses policyd (R-021/R-022 lessons). The orchestrator records plans, verdicts and queue state in the existing SQLite memory under `orchestrator:*` keys. (b) Tiered window control (design in this ADR; backends are later PRs): tier 1 accessibility tree (Windows UI Automation, Linux AT-SPI, macOS AXUIElement — the OS tells the agent where each component is, no screenshot needed); tier 2 shell/OS commands and keyboard shortcuts; tier 3 vision/screenshot grounding ONLY as a fallback when the tree is incomplete (custom-drawn UIs, canvas apps). Tier 3 is the slowest and most expensive, so it is never the default. ARCHITECTURE.md §4 already lists this hierarchy; this ADR fixes the order and the rule that vision is fallback-only. Screen-privacy rules from R-018 still apply (block/blur sensitive windows; human review before any UIA/screenshot path lands). (c) Scoped memory retrieval: memory stays in the existing local SQLite store, keyed per project/run (`orchestrator:<project>:*`); retrieval returns only entries relevant to the current task (prefix + recency), never a full dump; secrets are never stored (existing `_check_no_secrets`); memory never leaves the machine. No embeddings in this round (lightweight constraint). (d) VS Code integration (design only, no extension code this round): a VS Code extension talks to the existing localhost daemon API (the daemon already serves Runtime + Gateway + PolicyClient on a Unix socket / named pipe; the web UI is the precedent client). The workspace files are the ground truth — the extension shows orchestrator status and approvals, it does not become a second execution path. (e) OmniRouter as a gateway provider: no new gateway code is needed — it is an OpenAI-compatible endpoint. The provider is a named config: `{"name": "omnirouter", "kind": "openai-compatible", "base_url": "https://api.omrouter.com/v1", "model": "<catalogue model id>", "api_key_env": "OMNIROUTER_API_KEY", "egress": "cloud-backed"}` (endpoint verified against docs.omrouter.com, 2026-11-26; OpenAI format is the documented default). The key comes from the environment at call time only, never from the config file. Because it is cloud-backed, secret data never routes to it (existing `_is_eligible` rule) and it needs the same pre-approval/budget treatment as any cloud provider. A self-hosted OmniRoute-style gateway (e.g. `http://localhost:20128/v1`) works through the same `openai-compatible` kind with a local base_url and `egress: "local-only"`. NOTE: two products share the name (cloud "OM Router" at api.omrouter.com and self-hosted "OmniRoute"); the config above is the cloud one, and the docs must say so. (f) Lightweight constraint: the control plane (orchestrator + daemon + policyd) stays stdlib-only Python with no heavy dependencies; heavy work (model inference, vision grounding) lives in the models' own processes (Ollama, cloud CLIs). The orchestrator adds no new dependency and no new network egress beyond the gateway's existing provider calls.
Alternatives: A second model-calling path inside the orchestrator (rejected — duplicates the gateway's budgets, cloud gate and fallback chain, and would rot); letting the architect write files directly (rejected — bypasses policyd and verify(); integration must go through `run_tool`); vision-first window control (rejected — slowest and most expensive tier; the accessibility tree is both faster and cheaper); browser automation logged into the user's ChatGPT/Claude accounts to multiplex free tiers (CUT — see below); embeddings-based memory now (rejected for this round — a new dependency and index to maintain; prefix+recency retrieval covers the need, embeddings are a later ADR if recall proves insufficient); building the VS Code extension in the same round (rejected — the daemon API contract it needs is the design work in this ADR; code follows once the orchestrator is proven).
Consequences: Multi-model work becomes a first-class flow instead of ad-hoc gateway calls; every worker output is verified and attributable (provider + verdict recorded); budgets/queues make rate limits visible instead of silently failing; the CUT decision keeps the project inside providers' terms of service (see below). New risks R-026–R-028 (worker output as untrusted input, subtask sensitivity inheritance, verification bypass). Open/unproven items, marked honestly: the decomposition JSON schema is unproven against real architect models (the strict parser + deterministic fallback are the mitigation); no live Windows run exists for any of this (mock/Linux tests only; laptop confirmation pending); the VS Code extension and the UIA/AT-SPI backends are designed here, not built; the OmniRouter endpoint is documented, not live-tested (no key exists here).
CUT DECISION — browser multi-account multiplexing is NOT built: the maintainer's original plan included opening a browser, logging into several free ChatGPT/Claude accounts (e.g. 4 accounts in one browser) and routing work through them to evade free-tier limits. That is cut, with reasons: (1) it violates the providers' terms of service (multi-accounting to evade rate limits); (2) it is fragile in practice — CAPTCHAs, bot detection, session expiry and UI changes break browser automation constantly; (3) it is a credential risk — storing several accounts' sessions/passwords widens the blast radius of any leak. The legitimate replacement, which this ADR adopts: use every provider the user already has access to through its OFFICIAL CLI or API (Codex CLI, Claude Code, GPT CLI, Ollama, OmniRouter, …) with per-provider budgets and queueing — the same work gets done, inside the rules, and the gateway's fallback chain already implements the queueing.

## ADR-010 — Windows named-pipe server listener with a ctypes DACL
2026-11-23 · Status: Accepted
Context: ADR-008 deliberately left the named-pipe server fail-closed (R-017): the stdlib cannot create a pipe with an ACL, so any local process could have talked to `policyd` / the daemon (SECURITY.md adversary 5), and `NamedPipeListener.listen()` raised `NotImplementedError` — which blocked end-to-end `tool run` / `daemon start` / `doctor` on Windows entirely. The listener is the last piece of the Windows transport; the client side already existed.
Decision: (a) `core/transport.py` implements the server with `ctypes` `CreateNamedPipeW` and a `SECURITY_ATTRIBUTES` whose DACL is built by `_pipe_dacl_entries`: DENY `NT AUTHORITY\NETWORK` (S-1-5-2) first, then GRANT the current user's SID (from `GetTokenInformation(TokenUser)`) and GRANT `BUILTIN\Administrators` (S-1-5-32-544), all with `GENERIC_READ | GENERIC_WRITE` only. No other local account gets an ACE, so no other account gets access; the pipe name itself is local-only (`\\.\pipe\...`), and the NETWORK deny is defence in depth against remote logons. Administrators are granted because an admin already owns the machine (process memory, token theft), so denying them buys no security and would break admin diagnostics and a policyd run elevated under a different admin account. (b) Fail closed at every step: no Win32 API, no handler, ACL build failure, or `CreateNamedPipeW` failure all refuse to start — an ACL-less pipe is never served, and a mid-connection failure ends only that connection. (c) The accept loop uses overlapped `ConnectNamedPipe` polled every 500 ms against the stop event, and speaks the same JSON-lines protocol as the Unix-socket servers; `policyd.serve()` and `Daemon.serve_forever()` pass their real handlers (auth is checked inside, exactly as on POSIX) and return after serving instead of falling through to Unix-socket setup. (d) The Win32 calls sit behind a small `_CtypesWindowsPipeApi` interface so the listener logic is mock-verified on Linux with a fake API (20 tests: DACL policy, struct layouts, accept loop, every fail-closed path, policyd/daemon wiring). Structs use fixed-width types, not `ctypes.wintypes` (whose `DWORD` is 8 bytes on LP64 Linux), so layouts are checkable here: TRUSTEE 32, EXPLICIT_ACCESS 48, SECURITY_ATTRIBUTES 24, OVERLAPPED 32.
Alternatives: Keep failing closed and ship no Windows server (rejected — it blocks all end-to-end Windows use); grant only the current user and deny Administrators too (rejected — no security gain, breaks admin diagnostics); use `pywin32` instead of `ctypes` (rejected — a new dependency for one call site; the stdlib `ctypes` covers it); a NULL DACL with an application-level check (rejected — any local process could connect and the check would be the only defence).
Consequences: `policyd` and the daemon can now serve on Windows; end-to-end `tool run` / `daemon start` / `doctor` are unblocked pending laptop verification. R-017 moves from "blocked" to "implemented, mock-verified, awaiting live verification". HONEST LIMIT, recorded in code, this ADR and docs/WINDOWS_TESTING.md §6: the `ctypes` code has never run on a real Windows host — struct layouts and the call sequence follow the documented Win32 contracts, but only the laptop run proves it. Until that passes, the listener is implemented-but-unverified.

## ADR-009 — CLI provider env scrub, stderr redaction, pinned binary dirs, web UI session cookie
2026-11-23 · Status: Accepted
Context: Phase 2 left four risks open (R-010–R-013, ADR-004): CLI-model providers inherited the whole ambient environment (a compromised CLI could read API keys), `CliProviderError` carried up to 200 chars of raw CLI stderr into exceptions and logs (a hostile CLI could echo a secret there), bare CLI names resolved on the ambient PATH (a planted binary earlier on PATH wins), and the web UI authenticated browsers with a `?token=` query parameter (daemon token in browser history and server logs).
Decision: (a) R-010 — `run_cli_provider` builds the child environment from an allowlist (`CLI_ENV_ALLOWLIST`: PATH/HOME/TMPDIR/locale/TERM/USER only, secret-like names dropped) instead of inheriting `os.environ`; PATH is the pinned binary dirs first, then the default system dirs, so standard tools still work but no ambient PATH entry survives. Explicit per-call `env` overrides (the operator's own config) still pass through verbatim. (b) R-011 — CLI stderr passes through `redact_secrets()` (key=value assignments, Bearer tokens, sk-/sk-ant-/ghp_/AKIA/xox* shapes, PEM blocks) before it enters a `CliProviderError`; the exit code is kept, the secret is not. (c) R-012 — bare CLI names resolve only against pinned dirs: per-provider `cli_binary_dirs` on `ProviderConfig` > `OPENCOBOT_CLI_BIN_DIRS` env var > `/usr/local/bin:/usr/bin:/bin`; the ambient PATH is never consulted, for resolution (`_resolve_binary`), for the gateway `ping()`, or for the child PATH. Absolute paths still need an allowlisted basename and an executable file. (d) R-013 — the web UI drops `?token=` auth, token-carrying redirects and hidden token form fields entirely. A browser signs in once via `POST /login` (token in the body only) and receives a random session id in an HttpOnly, SameSite=Lax `opencobot_session` cookie (12h sliding, server-side in-memory store, `POST /logout` invalidates it); API clients keep using `Authorization: Bearer` / `X-OpenCobot-Auth` headers. No `Secure` flag: the UI serves plain HTTP on loopback only, where `Secure` would stop the cookie being set at all.
Alternatives: Keeping `?token=` for browser convenience (rejected — the token in history/logs was the risk); dropping stderr from errors entirely (rejected — a redacted first line keeps failures diagnosable); resolving CLI binaries from the ambient PATH when no pinned dir is configured (rejected — that is the spoofing hole; the defaults already cover the standard install locations, and the env var covers the rest).
Consequences: CLI providers can no longer see ambient credentials or be spoofed via PATH; hostile stderr cannot smuggle a secret into logs or audit; the daemon token never appears in a URL. Behaviour changes to know about: tests and operators that relied on ambient PATH for fake/real CLI binaries must set `OPENCOBOT_CLI_BIN_DIRS` or `cli_binary_dirs` instead; the web UI login flow is now POST /login + cookie (the old `?token=` test now asserts rejection). Risks R-010–R-013 are Fixed; the residual is that an operator who explicitly hands a CLI a key via per-call `env` owns that choice, and the session cookie is only as strong as the loopback-only bind (unchanged).
## ADR-008 — Windows adapter, PowerShell shell, named-pipe transport, UI Automation deferred
2026-11-23 · Status: Accepted
Context: ADR-001 deferred Windows to a stub (Linux-first MVP) because the build/test server is Linux. Phase 3 lands the Windows adapter so the same 22 tools run on a Windows laptop. The adapter was written and tested on Linux with mocks/fakes only (80 Windows tests: 46 adapter + 17 transport + 17 wiring); no Windows host was available to the builder, so every live behaviour still needs laptop verification (docs/WINDOWS_TESTING.md). Two hard constraints shaped the design: (1) a named pipe without an ACL would let any local process talk to `policyd` (SECURITY.md adversary 5), and the stdlib cannot set that ACL; (2) screenshot/GUI grounding needs Windows UI Automation, which cannot be verified headless.
Decision: (a) `adapters/windows/windows.py` mirrors `adapters/linux/linux.py` function for function; `tools/definitions.py` dispatches per call (`_is_windows()` / `_os_adapter()`), so the tool interface, schemas, levels and `verify()` are identical on both OSes. (b) On Windows `run_command` goes through the adapter's `run_powershell`: argv arrays only, never `shell=True`, never `cmd.exe`; each argument is wrapped in PowerShell single quotes with inner quotes doubled (`'` → `''`), the command is prefixed with the `&` call operator and passed as one `-Command` argument with `-NoProfile -NonInteractive`, so metacharacters (`;`, `|`, `$()`, backticks) stay literal data. Defence-in-depth blocklist: `WINDOWS_BLOCKED_COMMANDS` (sudo/su/doas/rm for parity plus format, diskpart, bcdedit, del, erase, takeown, powershell, pwsh, cmd) is refused in the adapter and again in the tool layer, plus conditional blocks (`reg delete`, `shutdown /r /s /…`, `rmdir /s`, `icacls /grant …`). The policy engine still gates `run_command` at Level 3 + approval. (c) Transport: the JSON-lines protocol is shared (`core/transport.py`); the client side is a stdlib `NamedPipeTransport` on `\\.\pipe\opencobot-policyd` / `\\.\pipe\opencobot-daemon`, while the server side (`NamedPipeListener`) fails closed with `NotImplementedError` until a `ctypes` `CreateNamedPipeW` listener with a current-user-only DACL lands and is verified on a Windows host — `policyd` refuses to serve on Windows until then, so `tool run` / `daemon start` / `doctor` cannot complete end-to-end on Windows this round. (d) `safe_resolve` uses `PureWindowsPath` with case-insensitive containment, lexical `..` collapsing plus symlink/junction/8.3 resolution via `os.path.realpath` on a real Windows host (injectable `resolver` seam for tests). (e) `git.exe` / `powershell.exe` are resolved via `shutil.which` (explicit `git.exe` first on Windows); `list_processes` parses `tasklist /FO CSV /NH`; `list_windows` uses PowerShell `Get-Process … MainWindowTitle`; `system_info` uses `platform` + `sys.getwindowsversion` + `wmic`, every call guarded with `None` fallbacks.
Alternatives: `cmd.exe` as the shell (rejected — PowerShell is the modern shell and its single-quote rule makes the data/code boundary explicit); an ACL-less named-pipe server so policyd could run now (rejected — any local process could issue policy decisions; fail-closed is the point); UI Automation / Graphics Capture screenshots in this round (rejected — untestable headless; deferred, honestly reported as unavailable); Recycle Bin via `SHFileOperation` (rejected for this round — not reachable from the stdlib; state-dir trash instead, same as the Linux fallback).
Consequences: File, git, process-listing, window-listing and PowerShell tools are wired for Windows and mock-verified on Linux; `screenshot` honestly reports unavailable, trash goes to the state dir (not the Recycle Bin), secrets stay out of scope (Windows Credential Manager per SPEC §6 is not implemented this round), `process_info` / `launch_app` are still Linux-shaped (`/proc`, `start_new_session`) and fail cleanly via the tool guard on Windows, and the CLI still hard-codes `daemon.sock` (`cli/opencobot_cli.py`) so the Windows CLI path is a later step. New risks R-015–R-019 (PowerShell execution policy, Windows PATH spoofing, named-pipe ACLs, UI Automation trust boundary, wmic deprecation). Live verification is tracked in docs/WINDOWS_TESTING.md; nothing here is live-verified until the laptop run passes.
## ADR-007 — Gateway config file; provider errors are no longer swallowed
2026-11-23 · Status: Accepted
Context: Live model testing (Ollama qwen2.5:0.5b) found three diagnostics gaps: (1) a failed runtime step reported "step 'list_dir' failed: allowed" because run_task preferred the policy decision reason over the tool's own error; (2) the CLI benchmark with the default model llama3.1 not installed scored 0.00 on all 7 tests with empty outputs, because Gateway.complete() caught the provider exception and returned a generic "no provider available" with no detail, and _call_http's error dict was then read as an "unexpected response"; (3) the gateway had no config-file override, so the default llama3.1 could only be changed in code.
Decision: (a) run_task reports the tool's own error when the step was allowed (decision reason only when the step was denied), and run_tool carries the execution error into its evidence; (b) _call_provider and Gateway.chat() surface an error dict's message (e.g. "model error: HTTP 404"), complete()/escalate() keep every provider error in their final error, and _gateway_complete prefers the gateway's error over "gateway returned no text"; the CLI benchmark probes the provider once before the suite and aborts with a clear error (naming model + cause) when it fails, and accepts a one-run --model override; (c) Gateway() loads ~/.config/opencobot/gateway.json (or $OPENCOBOT_GATEWAY_CONFIG) when present, overriding model/base_url (and timeout, api_key_env, budgets) on same-name providers and adding new named providers that declare a kind; unknown names without a kind fail loudly. Precedence: explicit configs > --model > config file > defaults. API keys are never read from the file.
Alternatives: Adding an "ok" flag to complete()'s result (rejected — the Phase 2 contract has no ok key; consumers now check error/needs_approval/text instead); making the benchmark tolerate a dead provider by scoring 0 (rejected — that was the bug: a missing model looked like a bad model); env-var-only model override (rejected — a file also documents base_url and extra providers, and the CLI already uses env vars for secrets only).
Consequences: A missing or failing model now fails fast with its real cause at every layer (gateway, runtime, CLI); the default model is changeable without code. The config file is a new trusted-local-config input: it can point a provider at any base_url, so it must only ever be written by the machine owner, like the CLI allowlist. Existing tests are unchanged in shape (complete() results gain no new keys).
## ADR-006 — Token `network` flag is enforced by the policy engine
2026-11-23 · Status: Accepted
Context: Capability tokens carried a `network: bool` flag (default False) that nothing checked, so a token issued without network access could still run `run_command` with `curl`/`wget`/`ssh` and exfiltrate data. The flag existed in `policy/tokens.py` since Phase 1 but was dead code.
Decision: Tools declare a static `network` capability (`ToolSpec.network`; only `run_command` is network-capable) and `tools.definitions.is_network_call(tool_name, args)` classifies each individual call from its argv — known network binaries (curl, wget, ssh, scp, sftp, rsync, nc, ncat, socat, aria2c, ftp, lftp, telnet, ping) and `git` network subcommands (clone/fetch/pull/push/ls-remote/submodule). The policy engine denies a network call when the token has `network=False`, with a clear reason, audit-logged. `policyd` re-classifies every check itself (caller's claim OR its own classification) so a caller cannot downgrade a network call by sending `network_call=False`. CLI: `token issue --network`, `tool run --network`, `policy check --network`; the flag defaults to False everywhere (fail closed). The token network flag is recorded as risk R-014 — it had no risk ID before this round.
Alternatives: Static per-tool denial only (rejected — `echo` via `run_command` is not a network call and should not need a network token); a network namespace / sandbox (rejected for this round — heavier, Linux-only, and the approval gate already bounds `run_command`); trusting the caller's `network_call` value (rejected — a compromised caller could lie; policyd now takes the max of both classifications).
Consequences: Network egress is now gated by the token, on top of the Level 3 approval gate — the flag is defence-in-depth, not a replacement for approval. Honest limit, documented in code: argv classification is not a sandbox. Arbitrary code run through `run_command` (e.g. `python3 -c` using urllib) can still reach the network, which is why `run_command` stays Level 3 and approval-gated regardless of the token flag.

## ADR-005 — Approvals are level-scoped and argument-bound
2026-11-23 · Status: Accepted
Context: Approvals were scoped to (token_id, tool_name) with a 600s expiry, so one benign `run_command` approval (e.g. `echo 42`) could be replayed for a different command with the same tool (R-007). That made the human's approval meaningless for the highest-risk tool.
Decision: An approval is now (token_id, tool_name, permission level, argument hash). `argument_hash()` is a stable SHA-256 of the canonical JSON of the arguments (sorted keys, `default=str`); only the hash is stored in `approvals.json` and in audit entries — never raw arguments, so sensitive arguments are not logged. A different level or different arguments needs a fresh approval; an approval recorded without a level can never match a real check (fail closed). The CLI (`policy approve --args-json/--level`, `tool run --approve` for the exact args about to run), the web UI approve path and the `policyd` approve op all bind approvals to the exact call.
Alternatives: Scoping to (tool, argument hash) without the level (rejected — the same arguments at a higher level are a different risk); storing raw arguments in the approval record (rejected — would leak sensitive arguments into a file and the audit log); keeping (token, tool) scoping and relying on expiry (rejected — the replay window was the bug).
Consequences: Every Level 3/4 call now needs an approval for exactly that call; existing tests and evals were updated to the exact-args flow. Approval replay for a different command is closed; the residual is that the approving human must still read the arguments they approve.

## ADR-004 — CLI-model providers and hybrid local/cloud routing division
2026-11-23 · Status: Accepted
Context: SPEC §8 requires the platform to work with any model, and the maintainer clarified Phase 2 must be powerable by ANY AI/model that runs in a CLI — opencode, kiro-cli, gpt cli, Amazon Q CLI, OpenCode — not just HTTP Ollama/OpenAI-compatible endpoints. SPEC §8.4 also requires an explicit work division ("tool kaam ko divide kr sake, kon ka kaam kise handle kre"), not just "local first, cloud fallback".
Decision: The gateway gains a generic CLI-model provider (`core/cli_providers.py`): subprocess, argv arrays only, no `shell=True`, binary from a user-config allowlist only (never from model output), prompt passed as data. Every provider — HTTP or CLI — declares an egress class: `local-only` or `cloud-backed` (Amazon Q CLI is `cloud-backed` by default; opencode/kiro/gpt default `local-only`; a `custom-cli` pointing at a cloud CLI must set `egress="cloud-backed"`). Routing is a real, testable table (`DEFAULT_ROLE_ASSIGNMENT`, `ROUTING_TABLE` in `core/model_gateway.py`): router/classifier, grounder and summarizer stay local; planner uses the strongest available and is the only role that escalates on high complexity; executor uses a reliable local tool-caller; verifier is a separate model or pure code check. Cloud escalation happens only if the user configured a cloud provider, only for public/personal data, never secret, and only on: JSON/schema fails twice, agent loops, verification fails, high complexity, or low confidence — with a cost estimate first unless pre-approved. Sensitivity: secret = local-only always; personal = user-approved cloud; public = any configured provider; unknown label fails closed as secret. See docs/GATEWAY.md for the full matrix.
Alternatives: HTTP-only gateway (rejected — excludes the maintainer's CLI models); per-provider free-form routing with no table (rejected — the division would be implicit and untestable); cloud-by-default escalation (rejected — violates SECURITY.md invariant 7, secret data never leaves the machine).
Consequences: Any CLI-running model can power OpenCobot with the same policy/budget/taint rules as HTTP models; CLI output is treated as untrusted/tainted data. New risks are recorded as R-010–R-012 (ambient env inheritance by CLI binaries, stderr leakage into logs, PATH spoofing). Built-in CLI argv templates are plausible defaults, not verified against real CLI versions — users can override `cli_argv_template`.

## ADR-003 — Tauri desktop UI deferred; simple web UI first
2026-11-23 · Status: Accepted
Context: SPEC §15 Phase 2 includes a Tauri desktop UI and approval UI. The maintainer approved the suggestion to do gateway + benchmark + read-only first and defer Tauri: a Tauri app needs Rust + Node + a display server, and the build/test server is headless Linux, so its UI could not be tested here; it is also the largest Phase 2 item.
Decision: Phase 2 ships a simple web UI instead (`ui/web.py`, stdlib-only `http.server`, binds 127.0.0.1 only, daemon auth token required, no JS framework, no external CDN): status, tools list, approvals (approve/deny), audit view, read-only toggle, kill switch, gateway providers, benchmark report. The Tauri + React desktop app stays on the roadmap for a later phase, when there is a machine with a display to test it on.
Alternatives: Tauri in Phase 2 (rejected for now — untestable here, would dominate the phase); no UI at all, CLI-only approvals (rejected — the maintainer asked for a browser-openable UI now, and approvals need a human-friendly surface).
Consequences: Approvals and monitoring are usable from any local browser today with no new dependency; the web UI is a stopgap, not the final desktop experience, and its `?token=` query-param auth (browser-history exposure) should be replaced by a session cookie before it is relied on widely (R-013).

## ADR-002 — Python-only policy engine for Phase 1, Rust deferred
2026-11-23 · Status: Accepted
Context: SPEC §6/§18 lists Rust as the candidate for the policy engine, executor and relay client, but leaves Python-only vs Python+Rust an open decision. The Phase 1 MVP must be built and fully tested on a Linux server overnight, with no live model.
Decision: Phase 1 ships a Python-only policy engine (`policyd` as a separate Python process, Unix-socket IPC, same permission/token/taint/audit semantics as the spec). Rust is deferred to a later phase, when the policy interface is stable and there is time to validate a second implementation against the same test suite.
Alternatives: Rust from day one (rejected for Phase 1 — slower to build/test, two implementations to keep in sync, no Rust test harness on the server); Python policy in-process (rejected — violates SECURITY.md invariant 2, the policy engine must be a separate process).
Consequences: Faster, fully testable MVP; the policy IPC protocol becomes the stable boundary, so a Rust `policyd` can replace the Python one later without changing the daemon, CLI or MCP server. The Python implementation must be treated as security-critical and human-reviewed despite being "only" Phase 1.

## ADR-001 — Linux-first MVP (Windows adapter deferred to a stub)
2026-11-23 · Status: Accepted
Context: SPEC §15 suggests Windows as the MVP OS, but the build/test server available for Phase 1 is Linux (no Windows, no display server, Docker containers cannot run on it). The user (maintainer) chose "Linux first — server pe poora test hoga" on 2026-11-23.
Decision: Phase 1 targets Linux: all 22 tools are implemented against the Linux adapter and verified by tests on Linux. The Windows adapter exists only as a stub raising NotImplementedError, behind the same tool interface, so Windows work later does not redo the core, policy, tools or gateway.
Alternatives: Windows-first per the spec suggestion (rejected for Phase 1 — code could be written but not executed or tested here); both OSes at once (rejected — doubles the untested surface).
Consequences: Phase 1 is genuinely runnable and testable end-to-end on Linux; Windows, macOS and GUI grounding (screenshot/windows) remain explicitly out of scope until a Windows machine is available to test on. ARCHITECTURE.md §4 platform note ("Windows is the suggested MVP target") is superseded for Phase 1 by this ADR, not silently ignored.
